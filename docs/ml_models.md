# Machine learning models

Feeds report section 5. All models are scikit-learn pipelines persisted with joblib in `source/src/botcierge/planner/mlmodels/`. Training code and the synthetic data generator are in `source/ml/` (inside the submission zip).

| ID | File | Predicts | Algorithm | Inputs |
|---|---|---|---|---|
| M1 | `m1_task_category.joblib` | Task category (8 classes) | TF-IDF (word 1-2 grams + character 3-5 grams) + Logistic Regression | Free-text description |
| M2 | `m2_platform.joblib` | Robot platform (8 classes) | Random Forest | Structured spec* |
| M3 | `m3_addons.joblib` | Add-on set (10 binary labels) | MultiOutput Random Forest | Structured spec* |
| M4 | `m4_skill_pack.joblib` | Skill pack / policy family (11 classes) | Random Forest | Structured spec* |
| M5 | `m5_robot_hours.joblib` | Robot-hours to finish the job | Gradient Boosting Regressor | Structured spec* |

\*Structured spec: task category (from M1 or customer), floor type, housing type, area, rooms, payload, budget, duration, hours/day, stairs, outdoor, pets, children, fragile items.

## Training data
All data is generated by `source/ml/generate_data.py` (seeded with `SEED = 2108`, reproducible).

**M2-M5:** 6,000 synthetic job specs. Labels come from operations-style rules with 3-4% label noise so the models generalise rather than memorise.

**M1 (free text):** 3,377 rows from three sources:
1. **Hand-written seed requests** in `source/ml/seed_requests/<category>.txt`: 695 short customer messages (83-95 per category), written by an LLM (Claude) to sound like real people messaging a home-services app in Singapore. They vary in length (one word to a few sentences), tone, spelling ("vaccum", "pls", "b4"), Singapore context (HDB, BTO, condo, landed, helper on home leave, CNY, void deck wake, ah ma), vague asks ("tidy", "security", "the pool"), messages that ask for two things (labelled by the main job), and borderline cases (for example "clean up after the party, cups and plates everywhere" is tidying, while "...floor is sticky from spilled drinks" is floor cleaning). No forum posts were copied.
2. **LLM paraphrases**: 372 rewordings of the seeds, written on the `~` lines under each seed. A seed and its paraphrases form one *group*.
3. **Noisy copies and templates** (training only): two copies of every training seed/paraphrase with deterministic typing noise (swapped or dropped letters, a dropped word, chat abbreviations like "pls"/"tmr", no punctuation), plus 100 rows per class from the original slot-filling template generator.

**Held-out evaluation.** A quarter of the groups in each category (174 seeds) are set aside as the test set. Only the original seed text is tested; the paraphrases of those seeds are dropped entirely, so no reworded copy of a test request is trained on. The split is stored in the `split` column of `task_descriptions.csv`, so `train_models.py` does not re-split at random. Training uses the remaining 521 seeds, 280 paraphrases, 1,602 noisy copies and 800 template rows (3,203 rows).

Held-out metrics (latest run): M1 acc 0.954 / macro-F1 0.954 on the 174 held-out hand-written requests; M2 acc 0.96 / macro-F1 0.84, M3 micro-F1 0.89, M4 acc 0.99, M5 MAE 3.8 h / R² 0.97.

For comparison, the previous M1 (template data only, random split) reported 1.00. That number only measured recall of the template word lists. Scored on the new held-out set, the old model gets 0.82. Re-drawing the group split with five other seeds gives M1 accuracies between 0.93 and 0.98 (mean 0.95), so ±3 points is within noise for a 174-row test set.

M1 per-class F1 on the held-out set: elder care 0.95, event serving 0.98, floor cleaning 0.98, home patrol 0.88, lawn care 0.96, pool cleaning 0.98, tidying 0.93, window cleaning 0.98. The remaining errors are the requests a person could also misread: "check on nai nai" (elder care, predicted patrol), "keep the house neat while I recover from surgery" (tidying, predicted patrol), "lego all over the floor pls pick up" (tidying, predicted floor cleaning), "clean the pool and if possible cut the grass around it" (pool, predicted lawn).

## How predictions automate the business
1. M1 removes the need for customers to classify their own chore.
2. M5 drives the quote (rental days) and the automatic deadline-feasibility check.
3. M2 picks the platform; a business rule then selects the cheapest in-stock robot meeting hard constraints.
4. M3 and M4 assemble the attachment list and skill pack, which become order line items and the robot's policy conditioning.
5. Edge cases (over budget, deadline risk, stairs, pets, children, fragile items) are flagged before checkout.

## Remarks
- M1's test set is written by the same author (an LLM) as its training data, so it shares a writing style. Real customer messages will probably score lower than 0.95. Once the app has real requests, label a sample of them and use that as the test set instead.
- Most requests contain a strong keyword (pool, grass, window, grandma), which is why a simple linear model does well. The hard cases are vague or two-part messages; the decomposer's `CATEGORY_CONFIDENCE_FLOOR` tells the customer when M1 is unsure, and they can pick the category themselves.
- M4 still scores near 1.00 because its labels come from clean rules on the structured spec.
- Humanoid is rare in the data (≈1%), which is why M2 macro-F1 is lower than accuracy.
- Re-train after changing `source/ml/taxonomy.py`; keep it in sync with `catalog/taxonomy.py`.
